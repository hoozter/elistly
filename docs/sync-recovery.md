# Account sync and local recovery

At signed-in startup, Elistly starts an account GET and displays that account's cached inventory or pending snapshot immediately. The visible refresh status distinguishes checking the account from sending edits. Cached views remain read-only until the response is verified. Failed refresh retains local data and shows an error; it does not create an empty account or claim successful sync. Profile and admin requests do not block inventory rendering. Initial setup is offered only after verified refresh confirms an empty account; cached emptiness cannot trigger setup over populated server data.

Server revisions are opaque strings, retained without timestamp truncation. Each queued snapshot carries its base revision and creation time. Only an acknowledged predecessor can advance a dependent snapshot's base; an unrelated cache refresh or another tab cannot grant overwrite authority. Web Locks serialize local queue mutations and same-account senders across tabs. The server's conditional write remains the cross-device authority. A response from an invalidated account cannot publish local state.

A valid queue against the unchanged server revision remains pending and drains sequentially after startup verification or reconnect. An exact remote match confirms a lost acknowledgement without another write. A divergent or provenance-less queue is copied, with all entries and revision metadata, into account-isolated recovery storage before it is removed from the active outbox. Archive verification failure leaves the queue intact. There is no automatic age-based deletion, merge, or last-writer-wins replacement.

**Review preserved local changes** downloads the complete local recovery archive, including original queued snapshots, account association, base revisions, timestamps and the remote snapshot observed at detection. Treat it as private account data. It is a recovery record, not a file to restore over the current account without review. Normal edits to the verified current inventory can sync while the archive remains preserved.

Sign-out refuses to erase pending edits or recovery archives. After downloading and checking the recovery file, the user can explicitly confirm **Remove downloaded browser copy**. This removes only the exact reviewed local archive; it neither changes server inventory nor silently accepts subsequently added recovery records. Keep the downloaded file. Invalid/unreadable browser state stays preserved and requires manual recovery.

A remote refresh cannot advance an open editor's base revision unless the application adopts the corresponding data. If the editor defers adoption, the view remains stale/read-only until reloaded. Unchanged server data does not cause an inventory redraw. Imports/restores cannot begin from an unverified cached view; a confirmed restore advances the model and revision together.

Settings **Export selected data** contains selected entities, entity types and categories only. Profile **Download inventory backup** includes all editable inventories, app settings and theme, but is not a full account/database backup. It excludes profile/authentication data, collector credentials, local pending/recovery data and separate offline source reports/receipts. Preserve recovery downloads and original reports separately; database backups must cover separate tables.

Verification uses synthetic browser accounts and durable local PostgreSQL with the real Worker handler, plus focused lifecycle tests. Production acceptance additionally requires an exact deployed revision and a read-only comparison of the signed-in browser, server inventory and preserved reference export. Local timings do not establish production latency or provider-session behavior.
